## Keep (続けたいこと)

### K1. 提供物としての「動くネットワーク」が達成できた

- 主目的の「制限のないインターネット提供」は両日とも達成。会場 IPUT のプロキシ環境を完全にバイパスし、参加者は端末側プロキシ設定なしで直接インターネットに到達できた
- 200 名規模 + Google DevRel Central のクルー / ゲストを受け入れて、致命的な接続不能事象は発生しなかった
- VLAN 11 (mgmt) / 30 (staff+live) / 40 (user) の 3 ゾーン L3 分離により、user セグメントが高負荷でも mgmt 系 (VyOS API / Grafana / SSH) の操作性が落ちず、当日のトリアージ操作が滞らなかった

### K2. 3 拠点フルメッシュ WireGuard が実運用で意図通り機能した

- r1-home (AS65002) / r3-venue (AS65001) / r2-gcp (AS64512) のフルメッシュ + eBGP + BFD 900ms 検知 / Connect-Retry 15s が「カタログ値」ではなく実環境で機能した
- IPv4 は dst-based、IPv6 は src-based PBR で経路を分ける設計が、当日の v6 不全の切り分けを助けた
- IPv6 デュアルプレフィックス RA はコミュニティイベント規模での実装事例として、JANOG57 と並ぶ参考事例を残せた

### K3. 「コンプライアンス境界としての shaper」原則を学べた

- 2026-04-09 (事前) の GCP DoS 検知 (NOC リードのスピードテストが起点) を踏まえて r2-gcp に egress shaper 500 Mbps + マシンタイプ up を準備
- 当日 (04-19) の DoS 再発で「マシンタイプ up は DoS 検知の対策にならない」反証が経験的に確定。今後 GCP 上のトランジット系を組む人にとって一級教材となるデータが取れた
- shaper policy 定義自体を残しておいた判断は正解。「shaper はパフォーマンス調整ではなくコンプライアンス境界」として恒常運用する設計原則に格上げできる

### K4. ログ・監視系がイベント中の根拠ベース判断を支えた

- nfcapd (NetFlow v9) アーカイブが 04-19 GCP DoS 申立て時の単一 TCP セッション 4.3 GB の証跡として実用的に機能した (3 分 36 秒の sub-burst まで特定可能)
- Loki + WLC msglog で 04-20 Wi-Fi 障害時に「ap-153-5 へのクライアント集中」「sw01 Gi 0/8 48 分ダウン」を当日中に root-cause まで辿り着けた
- Zabbix + Grafana 集約方針 (Uptime Kuma 廃止) は監視系統の単純化に寄与した

### K5. 責任分界点の明確化が IPUT 側に余計な負担を残さなかった

- 法執行機関対応のログ系統 (DNS / DHCP / NetFlow / NDP / GCS forensic 180 日保管) を NOC 側で完結させた
- AUP に「通信記録は運営が取得・保管」「日本国の法令に基づく要請があった場合は運営が対応」を明記し、参加者・IPUT 双方に対して責任分界を文書化
- IPUT 管理者を法的照会対応に巻き込まない構成が成立した。「会場を借りているコミュニティとして、施設に追加の管理コストを残さない」という event-wide な配慮が形になった

### K6. skill 駆動 VyOS 運用がチームとしての操作性を担保した

- VyOS API への curl ベース呼び出しを skill (`/vyos-show` `/vyos-retrieve` `/vyos-configure` `/vyos-save`) に統一しておいたことで、当日のトラブルシュートで Python スクリプト生成を経由せず即時に config 操作ができた
- 投入前に内容を提示するルールを skill 内で固めていたため、初心者と組んでも破壊的操作のレビューが自然に成立した。NOC リード単独に依存せず NOC チーム内で渡せる運用性を持てた
- 後任 NOC リード (専門家) が来た場合の handoff 資産としても機能する形で残せている

### K7. 専門インフラとしてのスコープ境界を保持した

- BwAI は Google 開発者コミュニティであり、ネットワークエンジニアコミュニティではない。ネットワークは会場電力・プロジェクタと同じ **専門インフラ** であり、コミュニティが内製化して継承する対象ではない、という判断を一貫して保持できた
- 「専門家がいれば提供する、いなければテザリングにフォールバック」は専門領域の合理的な継続性設計。広報 / スピーカーオフィス / LIVE 配信 / 会計 / 懇親会のような内製化対象とは性質が異なる
- この判断を保持したからこそ、コミュニティに「素人が運用できる程度に劣化させた半端なネットワーク」を継承資産として残す道を取らずに済んだ。半端な内製化は事故とトラブルシュート負債をコミュニティに残す

### K8. イベント専用 SSID が参加者体験の一部として機能した

- イベント主催者として「会場フリー Wi-Fi を提供する」のは最低限のインフラ保証だが、それに加えて **イベント専用 SSID が参加者のライブ感・特別感を構成する要素** として機能した
- 200 名規模の参加者 + Google DevRel Central のクルー / ゲストが同一の専用 SSID に接続することで、「このイベントのために用意された場」という共有体験が成立した
- SSID 名自体が BwAI ブランディングの一部として参加者の記憶に残り、ライブ配信アーカイブ・SNS 投稿・懇親会の話題等に現れる「イベントの顔」の 1 つとして作用
- これは純粋な技術品質 (帯域・遅延・可用性) の話ではなく、**イベント体験設計としてのネットワーク** の価値。テザリング fallback では構造的に代替できない付加価値として認識しておく

## Problem (改善が必要だったこと)

### P1. 専門領域スコープ境界の事前宣言不足

- ネットワークがコミュニティ内製化の対象外 (= 専門インフラ) であるというスコープ境界を、事前に明示宣言できていなかった
- 「専門家がいれば提供・いなければテザリング fallback」という継続性設計を、議論が始まる前に 1 ページで提示していれば、専門スコープ宣言として正しく伝わった。chat の流れで断片的に出したため「無責任な放棄 / 自己満足」と読まれる余地を残した
- 課題は判断そのものではなく、判断の **言語化と事前共有のタイミング**。Mini PRD と同時に「コミュニティ内製化対象 vs 専門インフラ」の整理を運営コアに渡すべきだった

### P2. 隣接ドメイン差を埋める説明戦略が不在だった

- 同じ GDG 運営チーム内の IPUT 窓口担当の専門領域 (常設組織ネットワーク + アクセス制御 / 倫理) と、NOC リードの専門領域 (イベントネットワーク) が **隣接ドメイン** だったことに、対話開始時点で気づけていなかった
- 同一用語 (VPN / ネットワーク / ログ / アクセス制御) が両ドメインで指す意味と慣行が異なる前提で対話を始めるべきだった。完全に異なるドメイン間より、同じ単語が出てくる隣接ドメイン間の方が「相手は理解している前提」で進んでしまい誤解が起きやすい
- 同じ説明を繰り返さざるを得なかった構造的原因は、平易化の不足ではなく **フレームワーク差そのものの可視化** が初手にできていなかったこと
- 対話履歴に苛立ちの発言が残ってしまった。当時の温度として残るが、後任が読んだとき「NOC リードが同じ運営チームの他役割メンバーを見下していた」と読める。これは今後のコミュニティ参加障壁になりうる。**疲労時の発言は隣接ドメイン差を踏まえた相互理解を阻害する**

### P3. 設計意図の事前共有が遅れ、業界事例参照を添えなかった

- VPN 必要性 / 論理分離 / 脅威モデル / 責任分界の説明を、運営チーム内 IPUT 窓口担当から懸念 (シャドー IT / AUP 抵触 / 制御不能なトンネル) が出た後に開始した
- 常設組織ネットワーク管理者目線では上記懸念は正論。これに対して個人技術論で反論しても、相手のフレームワーク内では「説得力ある懸念 vs 個人の例外主張」に見える
- 必要だったのは **業界事例参照** : JANOG 会場ネットワーク / ShowNet (Interop Tokyo) / コミックマーケット NOC / 各種技術カンファレンスで「短期独立 NOC が自前 VPN exit + 独立 AP 群で運営する」のがイベントネットワーク業界の標準実装、という外部資料を最初から添えること
- 業界事例があれば、議論は「個人の正論 vs 常設管理者の正論」ではなく「**常設ネットワークの慣行 vs イベントネットワークの慣行**」というフレームワーク差の話に置き換わり、「どちらも自分のドメインでは正しい、ただし今回はイベントだからイベント側の慣行を採る」で着地できた

### P4. ハンズオン中の体験品質を直接損ねた事象が発生した

- 04-20 11:00 以降、153 系 AP 配下で WebRTC 画面共有 (vdo.ninja) の瞬断が登壇/受講体験を直撃。詳細は [Wi-Fi 複合障害](./incident-2026-04-20-wifi-stability.md) 参照
- 04-19 の v6 不全により IPv6 比率が想定 30–40% → 実測 8%。Happy Eyeballs で v4 フォールバックされたため参加者からの苦情にはならなかったが、IPv6 で繋がる前提のハンズオン演習が混じっていたら直撃していた可能性
- 16F (sw02 配下) の AP3700 (Wave 1) は WPA3 SAE 非対応で接続失敗 → WPA2 PSK 切替後も Windows プロファイル残存で「PC 側プロファイル削除をお願いします」というユーザー側手数を要求するアナウンスが必要になった

### P5. スタッフ・登壇者・DevRel への事前ブリーフィングが薄かった

- 04-19 の GCP DoS 再発はスタッフ端末 (192.168.30.13) の Google Edge Cache からの 4.3 GB DL が起点。「r2-gcp 経由で >1 GB の単発 DL は事前に NOC に一声」というスタッフ向けの注意事項を出していなかった
- VLAN 30 が staff + live の混在用途で、配信機材と作業端末が同セグメントにいる状態の運用上のリスク (大容量 DL や検証トラフィックの混在) を事前に共有できていなかった
- 登壇者・配信担当・DevRel クルーへの「困ったとき」フロー (連絡先、SSID 一覧、AUP の要点) が口伝に近かった

### P6. 物理層の冗長性とラベル運用に弱点が残った

- WLC ↔ コアスイッチ間 (sw01 Gi 0/8 = T1-Trunk-WLC3504) が単一リンクで、48 分間のダウンが配下全 AP の CAPWAP control 断につながった。設計時に「ここは単一 SPOF」と認識していながら冗長化を後回しにした判断ミス
- sw02 → CT 200 (192.168.11.2 tcp 601) の syslog が Loki に届かず、CAPWAP の挙動を追うとき監視盲点になった (port flap が見えない状態で原因特定が遅れた)
- ap-161-1 (`a4:6c:2a:3c:29:84`、192.168.11.28) が 14:01 の Echo Timer Expiry 以降、当日中に復旧できず Not Joined のままイベント終了

### P7. NOC リード個人の判断ミスがインシデントの起点になったケース

- 04-09 の GCP DoS 一次検知はスピードテスト実行が起点。「lab 検証で 200 Mbps 律速だから本番も同程度」と過小評価し、egress カウンタの仕組み (送出を試みた量を全て計上) を見落とした
- 04-19 の v6 不全における RA preferred-lifetime の逆転 (OPTAGE 1800s / GCP 14400s) は memory 上の期待値 (OPTAGE 14400s 優先) と逆。事前検証で気付くべきだった
- `pd-update-venue.sh` (r1 task-scheduler 1 分間隔) が r3 の RA 設定を再書き換えしている可能性まで未検証で当日に持ち越した

### P8. NOC が「外から見られる前提」だった準備が緩んだ

- 来賓・スポンサー・DevRel クルーがツアーで NOC を見学する前提だったが、配線整理 / ケーブル長選定 / ラベル運用に後輩との温度差が現場で残った
- 「雑な配線 = 雑な運用」と外部から見なされるリスクが、NOC 単体ではなくイベント全体のシグナルになる視点を、構築前に共有できていなかった
- 詳細は [`noc-retrospective-2026-04.md`](./noc-retrospective-2026-04.md) §委譲で生じた抜け漏れ を参照

### P9. 後日対応がフォークしたまま終わっている

- ap-161-1 物理復旧 (16F、PoE LED / LAN リンク / sw02 ポート状態の現地確認)
- sw02 syslog 不到達の根本解消
- sw01 Gi 0/8 48 分ダウンの根本原因特定 (PoE 過電流 / ケーブル不良 / STP / Storm-Control の切り分け)
- IOS 15 系および Allied Telesis スイッチ MLD snooping の `no ipv6 mld snooping` 投入
- 7 台の Not Joined AP (`24:16:9d:f3:d4:60`, `f0:1d:2d:80:52:a0` 他) の棚卸し
- r2-gcp 削除前の GCS forensic bucket 残存確認 (180 日保管)

### P10. 多段伝言ゲーム構造で技術交渉の原意が消失した

- IPUT との技術交渉が「IPUT 技術担当者 → IPUT 窓口 (非技術) → GDG 側 IPUT 担当 (常設NW専門・イベントNW隣接ドメイン) → NOC リード」の **多段伝言構造** になり、各段で翻訳ロスと意図変質が発生した
- 中間者がイベントネットワーク専門外の場合、技術質問の精度を保ったまま伝達することが構造的に困難 (常設ネットワーク管理者目線での質問再構成や、隣接ドメインでの慣行差を含めた翻訳が発生する)。具体例 :
  - 「プロキシ解除済み」と聞いた当事者の認識が、実際には DIRECT_LIST 許可分のみ通る状態だった
  - IPUT 側が示した「臨時 SSID + PW」が業務用 WLC の話なのか家庭用ルーターの話なのか、伝言段では区別がつかない
  - 「VPN は学校のセキュリティポリシーに引っかかりそう」が、IPUT 技術担当者の評価か中間者の推測かが不明
- 同一ドキュメントを全員で参照する非同期交渉を複数回要望したが、構造上解消されないままイベントに突入した
- 結果として同じ説明を別経路で繰り返す / 解釈違いが事後発覚する / NOC リード側の疲弊が累積する、という負債が発生

## Try (次回への引き継ぎ)

### T1. 劣化 tier の事前公開と、後任 NOC 専門家がいる場合のみの handoff 整備

- 「次回 NOC リードが誰でも動く Runbook」を必須成果物にするのは過剰 (= 半端な内製化を強制し、コミュニティに専門領域の負債を残す)。代わりに **劣化 tier を事前公開** する
- イベント提案フェーズで運営コアに 3 tier を提示 :
  - **Tier 1 (フル NOC)** — 専門家チームがいる場合。今回の VyOS 3 拠点 + IPv6 デュアル + GCP 連携構成。ネットワーク品質が最大、かつ **イベント専用 SSID による参加者体験の付加価値** (K8 参照) も確保
  - **Tier 2 (最小 VyOS)** — 専門家 1 名のみの場合。VyOS 1 台 + 会場 AP 借用 or 単一自前 AP。プロキシ回避と VLAN 分離だけ確保、専用 SSID は最小構成で維持
  - **Tier 3 (NOC 不在)** — 全員テザリング、または会場提供 Buffalo を素のまま使用。配信のみ最小限の VPN exit で確保。**イベント専用 SSID による体験設計は成立しない** (参加者は各自のキャリア回線、あるいは会場汎用 SSID を使う)
- 各 tier に「何が確保され、何が確保されないか」を明記する際、**技術品質だけでなく参加者体験面の差** も併記する (Tier 3 はイベント感としての Wi-Fi 体験が無い)。運営コアが事前に承知して開催判断する状態にする
- NOC 不在は「緊急事態」ではなく「計画された劣化状態」として扱う
- Runbook / handoff ドキュメントは Tier 1 が成立する場合の **資産として optional** に整備。後任 NOC 専門家が来た場合に渡せる形で残す :
  - VyOS config snapshot (`docs/configs/`) と構築 → 検証 → 当日変更履歴 → 撤収のシナリオ
  - skill 運用と当日インシデント別 playbook
  - 監視ダッシュボード (Grafana / Zabbix / Loki) の見方と異常時初動
  - GCP / WLC / Proxmox の認証情報引き継ぎ手順
- 「Runbook が無ければ次回に入れない」という制約は置かない。専門家が来ない次回は Tier 3 で開催する選択肢を運営コアに残す

### T2. 設計意図の 1 枚資料を、技術論争が起こる前に配る

- 1 枚資料の **最上位 2 段** に以下を並べる :
  1. **コミュニティ内製化対象 vs 専門インフラ境界** — 広報 / スピーカーオフィス / LIVE 配信 / 会計 / 懇親会 等 (内製化対象) と、ネットワーク / 会場電力 / プロジェクタ 等 (専門インフラ、外部専門家 or fallback) の区別
  2. **常設ネットワーク vs イベントネットワーク 評価フレームワーク差** — JANOG 会場ネットワーク / ShowNet (Interop Tokyo) / コミックマーケット NOC 等の業界事例を引用し、「短期独立 NOC が自前 VPN exit + 独立 AP 群で運営する」のがイベントネットワーク業界の標準実装であることを明示
- その下に「なぜ自前ネットワークか / なぜ VPN か / IPUT 既設ネットワークへの影響はゼロである根拠 / 責任分界点 / ログ設計 / セキュリティポリシーとの整合」を **隣接ドメイン専門家向け** FAQ 形式で
- 既に [`docs/network-overview.md`](../network-overview.md) があるが、(a) スコープ境界の事前宣言 (b) 常設 vs イベントのフレームワーク差と業界事例 (c) 常設目線の懸念 (シャドー IT / AUP 抵触 / 外部からの検知) への先回り回答 が含まれていない。これを増補する
- 配布タイミング : Mini PRD 作成と同時、設計確定前。質問が出てから書き始めるのではなく、質問を予防する形で出す

### T3. コミュニケーション self-check ルール

- 同じ説明を 3 回以上繰り返しそうになったら、相手のメンタルモデルを推定し直す (相手は何を分かっていて、何を分かっていないのか / 相手はどの専門領域から見ているのか / 同じ単語が両ドメインで何を指すのか)
- 相手の懸念を「言い換え」で返してから自分の主張を述べる (例: 「『VPN で IPUT のネットワークがブラックボックス化される』という懸念ですよね。それに対しては…」)
- 苛立ちの発言は対話履歴として永続化される。後任 NOC リードや次回参加検討者が読んだとき「ここは関わりたくない」と思わせる。**温度のある返答は offline (DM や口頭) に逃がす**
- 疲労時にこのルールが破綻しやすい。疲労を察知したら「明日返信します」で離脱する選択を持つ

### T4. MTG 運用原則を NOC チーム MTG にも適用

- 全体共有が必要なもののみを扱う
- 脱線すれば offline (DM や個別 1on1)
- 開催目的を明確化して、目的が無いなら開かない
- NOC チーム内 MTG は技術論に脱線しがちなので、特に「目的の事前明示」を徹底する
- 役割リードは事前に振る (途中からの追加は厳しい)。NOC 内サブ役割 (WLC / VyOS / 監視 / forensic) を事前に振り、各自 RACI で R を持たせる

### T5. 事前検証プロトコルを「構成全体」から「access port × 1 ポート」まで分解する

- 各スイッチの access port にクライアントを直接挿し、IPv6 GUA 付与・外部 v6 通信成立を 1 ポートずつ確認する手順を SOP 化
- AP 経由検証は trunk + 無線ブリッジで multicast 挙動が変わるため、access port 固有の問題 (MLD snooping 起因の RA/NS drop など) を覆い隠す。AP 検証「だけ」で完了とみなさない
- IPv6 比率を Cloudflare Radar 等の外部統計と Grafana で常時比較表示し、構築段階で乖離を検知する

### T6. WLC アップリンクと監視盲点をイベント前に潰す

- WLC ↔ コアスイッチ間は LACP 2 ポート以上で必須冗長化。次回構築チェックリストの最上位に配置
- 全スイッチの syslog 到達ヘルスチェックを Zabbix テンプレート化
- WLC の DFS / chan-width / CleanAir ED-RRM の「会場プリセット」(W56 除外、≤40MHz、ED-RRM 無効) をテンプレ化して構築時に一括適用

### T7. AP 世代差を設計の最上位制約として扱う

- `show ap inventory all` での型番百位 (37xx=Wave 1 / 38xx=Wave 2) ベースの世代分類を構築前インベントリの必須項目に
- 混在環境では機能の下限を Wave 1 に合わせる (WPA2 PSK + PSK-SHA2 + PMF Optional + FT Adaptive) ことを設計原則として明文化
- WLAN セキュリティ変更時は「Windows / Android / iOS のプロファイル削除手順」をユーザー向けに事前準備

### T8. 関係者向けブリーフィングと連絡フローを整備する

- スタッフ向け技術ブリーフィング (高帯域操作・テスト系・大容量 DL の事前一声ルール、r2-gcp 経由の制約説明) をイベント前日に開催
- 登壇者・配信・DevRel 用の事前接続検証 slot を本番前日のリハーサル時間内に確保
- 中央プロジェクタ / Slack / 口頭の 3 chan で発信できる「障害アナウンステンプレ」を NOC ハンドブックに収録

### T9. 「コンプライアンス境界としての shaper」を恒久設計原則に

- GCP / GCE 上のトランジット系には egress shaper を恒常配置 (1–2 Gbps、`qos policy shaper` で interface egress に常時適用)
- マシンタイプアップグレードと shaper 解除は独立判断 (A の理由で B を外さない) を VyOS 設計書 (`docs/design/gcp-integration.md`) に明記
- Cloud Monitoring アラート (instance/network/sent_bytes 分単位) を初期投入時から有効化

### T10. シニアの暗黙知 verbalize を必須化するハンドブック構築

- `docs/operations/noc-handbook.md` (新設予定) に「定石 / なぜ / 委譲時に必ず言う一言」の 3 点セット形式で再構成
- 物理 literacy 系 (PoE インジェクター方向、SFP 挿入向き、コンソール pinout、PoE 規格と AP 世代の対応、ケーブル長選定、整理整頓) は構築前に handbook + 実物で 30 分のブリーフィング
- 設計書 (`docs/design/`) 各ファイルに「将来想定 / 拡張余地」セクションを設け、委譲時に併読させる

### T11. 後日対応の残タスクを optional でなく milestone として持つ

- ap-161-1 物理復旧と sw01 Gi 0/8 根本原因特定は「次回イベント前」を期限に NOC 内で担当者を決める
- IOS 15 系 / Allied Telesis スイッチの MLD snooping 無効化は機種・管理 IP の確定 → 投入計画 → 暫定対応 (RA lifetime 0) の解除タイミング決定までを 1 つの mini-project に
- r2-gcp 削除と GCS forensic bucket (180 日保管) の整合は、forensic 系統だけ別プロジェクトとして残し、networking 系の VM のみ削除する手順を文書化
- 借用品 MS-01 (venue Proxmox) は GCS 転送完了確認後に初期化 → 返送。**転送前の初期化は厳禁** (rsyslog / nfcapd の forensic データを失うため)。返却完了を後日対応 milestone の最終条件とする

### T12. イベントネットワーク業界事例参照カードの整備

- イベントネットワーク業界事例集を 1 枚にまとめて常時参照できる形で保持する
- 収録対象 :
  - JANOG 会場ネットワーク (各 JANOG ミーティング、設計と運用の公開資料)
  - ShowNet (Interop Tokyo) — 業界最大級のイベントネットワーク事例
  - コミックマーケット NOC — 大規模来場イベントでの短期 NOC 構築
  - 各種技術カンファレンス (Cloud Native Days、PyCon JP 等) の NOC 構築事例
- 各事例について「短期独立 NOC / 自前 VPN exit / 独立 AP 群 / 自前ログ管理」がどう実装されているかを 1-2 行で要約
- 用途 : 常設ネットワーク管理者 / 隣接ドメイン専門家との対話で「これは個人の主張ではなく業界慣行」と即座に提示できる reference カードとして
- 配布タイミング : 設計意図の 1 枚資料と同梱、または別添付として Mini PRD 段階で

### T13. 多段伝言を解消する共有ドキュメント / 直接対話の原則

- 技術交渉は **共有ドキュメントベースの非同期交渉** を原則とする。中間者が「翻訳」して伝えるのではなく、原文ドキュメントを **IPUT 技術担当者を含む全関係者** が同時に参照する
- 具体的運用 :
  - 要求事項 / 設計意図 / FAQ を Markdown 1 本にまとめ、URL を全関係者 (IPUT 技術担当者含む) に共有
  - 質問・回答もそのドキュメントの comment / issue に集約。チャット上での口伝による拡散を避ける
  - 中間窓口を通すのは「アクセス手配」「日程調整」のような非技術事項のみに限定
- 中間者経由の質問が来た場合、回答は「ドキュメントに追記しました、これを技術担当者にも共有してください」の形で返し、ドキュメント上で議論を集約する
- 直接対話が必要な技術論点については、**NOC リード ↔ IPUT 技術担当者の直接コミュニケーション (メール / MTG)** の場を 1 回設ける。中間者は同席してよいが、訳す役回りは発生させない
- これは「中間窓口を不要と言っている」のではない。中間窓口は運営フロー全体の調整に必須。**技術交渉の翻訳役を中間窓口に背負わせない** という線引きを事前に共有することが要点

## 個人として持ち帰る点

- **専門領域スコープ境界は事前宣言する**。「ネットワークはコミュニティ内製化の対象ではなく、専門家がいれば提供・いなければテザリングへ劣化、という構造」を、議論が始まる前に 1 ページで提示する。事前に境界を立てれば後からの弁明が不要になる
- **「相手が知っているか知らないか」ではなく「相手のフレームワークが何か」を最初に問う**。隣接ドメインの専門家であっても、フレームワーク差で誤読は生じる。「相手はどの専門領域から見ているのか / 同じ単語が両ドメインで何を指すのか」を最初に確認する
- **隣接ドメイン間の対話は同一用語が異なる慣行を指す前提で始める**。常設ネットワークの「VPN = リモートアクセス手段、監査対象」とイベントネットワークの「VPN = プロキシ / ポート制限回避のトンネル、独立 NOC の標準ツール」は同じ単語で異なる慣行。完全に異なるドメイン間より誤解が起きやすい
- **業界事例参照は「個人の正論」を「業界慣行」に変換する装置**。常設管理者目線の懸念に対して個人の技術論で反論するのではなく、JANOG / ShowNet 等の事例を最初から添える方が、フレームワーク差として相互理解できる
- **疲労時のコミュニケーションは負債を生む**。永続化される対話履歴に苛立ちの発言が残る判断コストは、その瞬間の感情的解放に見合わない。疲労を察知したら離脱の選択を持つ
- **「lab 値 = 本番上限」と決めつけない**。GCE egress カウンタのように、計測する側のメトリクスがどう動くかを含めて事前検証する
- **memory 上の期待値と実機の差分を構築直後にもう一度確認する**。RA lifetime 逆転 (memory: OPTAGE 14400s / 実機: OPTAGE 1800s) を当日まで持ち越したケースが該当
- **GCP 申立てのような外部コミュニケーションは、NetFlow 証跡 + 図解 + 過去 ticket 引用を最初から準備して書く**。今回の英文申立て 2 通はテンプレとして残す
